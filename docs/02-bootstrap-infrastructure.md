# 02 · Bootstrap infrastructure (shared layer)

*Step-by-step guide · `infrastructure/terraform/bootstrap/` · Vojislav Stefanović · v1, 15.11.2026*

**What this is and why.** The assignment asks for an App Service *on an existing Linux App Service
Plan* and, as a bonus, monitoring of *an existing SQL Server*. In a real company those would already
exist, owned by a platform team. This layer simulates that: it creates the shared, long-lived
resources once — resource group, the Linux App Service Plan, the virtual network with its two
subnets, the SQL Server behind a private endpoint, private and public DNS zones, the Log Analytics
workspace and the storage account that holds Terraform state for everything else. Keeping it in its
own Terraform root gives it a separate blast radius: destroying an environment can never take the
plan, the SQL Server or the state storage with it.

An **App Service Plan** is the compute (VM size and count) that one or more Web Apps run on; the
apps themselves are created later and only *reference* it. A **private endpoint** gives a PaaS
service (here SQL) a private IP inside the VNet so traffic never crosses the public internet; the
matching **private DNS zone** makes the service's normal hostname resolve to that private IP from
inside the VNet.

## 1. Resources created

| Resource | Name | Description |
|---|---|---|
| Resource group | `rg-uniqa-shared` | Container for everything (shared and per-environment) in this assessment |
| App Service Plan | `asp-uniqa-linux` | Linux, **B1**; the "existing plan" the Web Apps are placed on |
| Virtual network | `vnet-uniqa` 10.10.0.0/16 | Private network for integration and endpoints |
| Subnet | `snet-appsvc-integration` 10.10.1.0/24 | Delegated to `Microsoft.Web/serverFarms`; App Service VNet integration (outbound) |
| Subnet | `snet-private-endpoints` 10.10.2.0/24 | Hosts private endpoints (inbound) |
| Private DNS zones | `privatelink.database.windows.net`, `privatelink.azurewebsites.net` | Linked to the VNet; resolve SQL / Web App hostnames to private IPs |
| SQL Server | `sql-uniqa-bisn5` | v12.0, TLS 1.2, SQL auth with generated password; public access limited to the admin IP by firewall rule |
| Private endpoint | `pe-sql-uniqa-bisn5` | SQL Server in `snet-private-endpoints`, registered in the SQL private DNS zone |
| Log Analytics | `log-uniqa` | PerGB2018, 30 days; sink for diagnostics and Application Insights |
| Public DNS zone | `stefanovic-devops.xyz` | Azure DNS; custom-domain records are created here by the application layer |
| Storage account + container | `stuniqatfstatebisn5` / `tfstate` | Remote state for the application (`dev.tfstate`, `test.tfstate`) and monitoring (`monitoring.tfstate`) roots |

The random suffix `bisn5` is produced by `random_string.suffix` so the SQL Server and storage
account names are globally unique.

> [!NOTE]
> This root uses **local state** on purpose: it creates the storage account that every other root
> uses as backend, so it cannot use that backend itself. `terraform.tfstate` is `.gitignore`d and
> contains the SQL admin password — keep it where you keep other secrets.

## 3. Apply

### 3.1 Prepare the variables file

```bash
cd infrastructure/terraform/bootstrap
cp terraform.tfvars.example terraform.tfvars
```

Edit `terraform.tfvars` and set `subscription_id`, `admin_client_ip` (`curl -4 ifconfig.me`) and
`location = "francecentral"`; the file is ignored by git.

### 3.2 Initialise, plan, apply

```bash
terraform init
terraform plan -var-file=terraform.tfvars -out=tfplan
terraform apply tfplan
```

`init` downloads `azurerm` and `random`; the plan shows 18 resources to add and `apply` takes about
6–8 minutes, most of it the SQL Server and its private endpoint.

> [!WARNING]
> Azure Resource Manager is eventually consistent. On the first run the private DNS zone link and the
> SQL private endpoint occasionally returned `404` right after creation, and once Terraform reported
> *"Provider produced inconsistent result after apply"*. Re-running `terraform apply` with the same
> plan inputs converged every time; see [06-troubleshooting.md](06-troubleshooting.md) §3 for the
> `terraform import` commands used when a resource existed in Azure but not in state.

### 3.3 Read the outputs

```bash
terraform output
terraform output -raw sql_admin_password   # sensitive, print only when needed
```

The outputs feed the next layers: `tfstate_storage_account_name` goes into
`infrastructure/terraform/backend.hcl`, `sql_server_name` and `sql_admin_password` become
`TF_VAR_*` exports in [03-application-infrastructure.md](03-application-infrastructure.md).

## 4. The one manual step: delegate the domain

Azure DNS hosts the zone, but the registrar still points the domain at its own nameservers until
you change them. This cannot be automated from Azure.

### 4.1 Get the Azure nameservers

```bash
terraform output -json dns_zone_name_servers | jq -r '.[]'
```

Prints four `ns1-0X.azure-dns.com`-style hostnames (the trailing dot is part of the record).

### 4.2 Set them at Namecheap

In *Domain List → Manage → Nameservers → Custom DNS* enter the four names (without the trailing
dot) and save; propagation took under 30 minutes for this domain, but can take up to 48 hours.

> [!TIP]
> `dig NS stefanovic-devops.xyz +short` must list the Azure nameservers before you enable
> `enable_custom_domain = true` in the application layer — App Service validates the `asuid` TXT
> record and the managed certificate issuance needs the CNAME to resolve publicly.
